# ADR-001 · Backend independiente y transición

[Seguro] Fecha: 2026-10-06 · Base: `ecf2864955cae6b692f98bbcd992d5f1085755e0` · #144/#145. **Estado: PROPUESTO, PENDIENTE de aceptación.** El destino Node.js/NestJS fue solicitado en la épica; este ADR no acredita implementación ni reemplaza la descripción vigente de [doc 06](../../06-arquitectura-y-stack.md).

## Contexto y propuesta

[Seguro] Hay un monorepo pnpm/Turborepo, Next.js, contratos Zod/core, SQL transaccional/RLS y seis Edge Functions; no hay un backend Nest entregado. El usuario confirmó un desarrollador y datos exclusivamente de pruebas. [Probable] Conservar el SQL y migrar transportes por módulo reduce el trabajo simultáneo de ese desarrollador.

## Autorización y fuente de dominio

[Probable] El rol API tendrá `NOBYPASSRLS`, no será propietario de tablas, y solo tendrá SELECT/EXECUTE/CRUD trivial estrictamente necesarios. Para cada consulta autenticada, incluso lectura: reservar una conexión, abrir transacción, validar la sesión en Nest, resolver identidad a `public.users.id`, establecer contexto **local de transacción**, ejecutar y hacer commit/rollback antes de devolverla al pool. Actor/roles nunca llegan desde un DTO de cliente. Toda ausencia de contexto falla cerrada.

[Probable] Durante #149, un adaptador de la identidad Supabase verificada mantendrá la semántica de `auth.uid()`/`auth_user_id()`; #164 sustituirá esa dependencia con el mismo perfil de dominio. Jobs/webhooks usarán roles separados con grants a funciones de servicio concretas, sin exponer funciones privadas a la API pública. Cada `SECURITY DEFINER` requiere propietario, `search_path`, grants y validación del actor documentados; se prueban pooling entre actores, multirol y acceso sin contexto con usuarios de runtime reales.

[Seguro] El dominio se conserva según docs [02](../../02-roles-y-permisos.md), [04](../../04-modelo-de-datos.md), [07](../../07-api-y-backend.md), [08](../../08-reportes-y-estadisticas.md) y [11](../../11-legal-seguridad-privacidad.md): V1–V6; R1 y consentimientos separados; último ADMIN; capacidad comercial; COACH sin notas/desmarcado; asistencia única y lote ≤500; historia; UTC/Chile; `77.8 %` y denominador cero → `null`. [Probable] Nest coordina esas invariantes mediante SQL y no vuelve a implementar las métricas en servicios.

## Continuidad de identidad

1. [Probable] #150 inventaría con fixtures sintéticos perfiles ACTIVE/INVITED/MANAGED, proveedor/subject, hashes compatibles, FK, triggers, recuperación, invitaciones y rutas de avatar basadas en Auth UUID. No exportar secretos ni hashes reales a evidencia.
2. [Probable] #161 mueve archivos y su mapa de propietarios antes de retirar Storage/Auth. `public.users.id` y todas las FK de historia se conservan; Auth UUID también se preserva o queda en un mapa privado explícito para las referencias externas existentes.
3. [Probable] #162/#163/#164 ensayan credenciales, Google/Apple, vinculación, recuperación y términos. Un hash importable se verifica contra cuentas sintéticas; un hash no compatible requiere recuperación aceptada, nunca contraseña inventada. MANAGED sigue sin credenciales.
4. [Probable] Sesiones anteriores se revocan/renuevan con aviso y un corte planificado; enlaces/token de recovery e invitación anteriores se atienden o reemiten según su vigencia sin habilitar replay. No asumir que JWT/refresh Supabase funcionarán como tokens propios.

## Corte y reversión

[Probable] Secuencia preferida: API sobre DB/Auth actual → dominio por módulos → worker/integraciones → Storage → identidad → PostgreSQL independiente → QA/ensayo → corte → observación → retirada. Una base escritora y un ejecutor de correos/push/billing por capacidad. Los flags de encaminamiento cambian módulos completos; las funciones SQL preservan transacciones y locks durante convivencia.

[Seguro] Hoy no hay usuarios reales ni producción, según el usuario. [Probable] Se recomienda completar el corte antes de admitir usuarios reales y conservar un backup de prueba restaurable. Si el lanzamiento con Supabase ocurre antes, se debe repetir MIG-01 con volúmenes, contratos de pago y continuidad reales; ese cambio de contexto invalida usar automáticamente una ventana o rollback de entorno de prueba.

[Probable] Ensayo de corte: congelar escrituras/ejecutores, drenar y registrar reservas/efectos inciertos, snapshot DB + inventario de objetos/identidades, importar, reconciliar UUID/conteos/checksums/ledger, probar permisos y login, activar destino y observar. Antes de la primera escritura destino puede restablecerse el origen intacto. Después, rollback requiere nueva congelación y reconciliación de las escrituras/eventos posteriores, o recuperación hacia adelante; volver al snapshot viejo perdería historia.

[Suposición] Objetivos para discusión: RPO ≤15 min, RTO ≤4 h, ventana 2 h y observación 7 días. [Seguro] Ninguno está aprobado ni medido; #166/#167 deben aportar tiempos reales y aceptación antes de usarlos como garantía. No se retiran receptores Supabase si contratos Mercado Pago aún los necesitan.

## Alternativas y aceptación

| Alternativa | Evaluación propuesta |
| --- | --- |
| [Probable] Reescribir SQL/RLS y API a la vez | [Probable] Mayor superficie de regresión para un desarrollador; preferir reutilizar SQL y cambiar transporte. |
| [Probable] Microservicios/Redis desde el inicio | [Probable] Más despliegues, permisos y conciliación sin requisito actual; PostgreSQL cubre la cola propuesta. |
| [Probable] PostgreSQL autogestionado barato | [Probable] Traslada backups/PITR, parcheo y recuperación al único desarrollador; preferir DB gestionada y cotizar operación. |
| [Probable] Corte total inmediato | [Probable] Posible antes de lanzamiento únicamente después del ensayo de paridad/identidad/archivos; no omitir garantías por tratarse de datos de pruebas. |

[Seguro] Aceptación pendiente: titular del proyecto para alcance/identidad, responsable de operación para proveedor/recuperación, y desarrollador para compatibilidad/seguridad.
