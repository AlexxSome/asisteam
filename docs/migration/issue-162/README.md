## Identidad y seguridad

- [Seguro] `public.users.id` permanece como identidad de dominio. `auth_user_id` referencia `app_private.auth_subjects`, un mapa de UUID/email compatible con sujetos GoTrue existentes. Las cuentas MANAGED siguen sin credencial; el claim dirigido reutiliza la RPC canónica y conserva membership/asistencia. Una cuenta nueva nativa no necesita fila en `auth.users`.
- [Seguro] Argon2id mantiene parámetros PHC: 19.456 KiB, dos iteraciones, paralelismo uno, hash de 32 bytes. El verificador soporta bcrypt `$2a/$2b/$2y` con coste 4–14 y rechaza contraseñas que bcrypt truncaría a 72 bytes UTF-8. El rehash ocurre tras verificar credenciales y comparar el hash bajo bloqueo. #164 debe importar solo hashes compatibles; otros usuarios requieren recovery.
- [Seguro] Registro/reset/cambio de contraseña consultan HIBP mediante k-anonymity (prefijo SHA-1 de cinco caracteres, `Add-Padding`, 3 s); fallo de proveedor bloquea la escritura. Contraseñas 10–128 caracteres, sin normalización silenciosa. Referencias: [node-argon2](https://github.com/ranisalt/node-argon2), [bcrypt.js](https://github.com/dcodeIO/bcrypt.js), [Pwned Passwords](https://haveibeenpwned.com/API/v3#SearchingPwnedPasswordsByRange).
- [Seguro] Access JWT HS256: issuer configurado, audience `asisteam-api`, 15 min, sujeto/session UUID; no roles del cliente. Toda operación de dominio valida familia vigente en PostgreSQL antes de ejecutar y antes de commit. El bloqueo SHARE serializa con revocación.
- [Seguro] Refresh aleatorio de 256 bits se guarda como SHA-256, rota una vez y conserva consumo; reutilizarlo revoca la familia incluso si otro refresh ganó concurrentemente. Familia: 30 días absolutos. Logout revoca el dispositivo; reset/cambio revocan todas las familias y consumen todos los recovery pendientes.
- [Seguro] Recovery: 256 bits, hash SHA-256, 60 min, consumo/password/revocación atómicos. Respuesta pública idéntica exista o no cuenta, con fase de envío igualada a 2,1 s y Resend acotado a 2 s. No hay garantía de entrega real en QA local. Los mensajes/logs no contienen credenciales, tokens ni PII.
- [Seguro] Al sustituir contraseña de un sujeto ya importado se revocan sus sesiones GoTrue y se deshabilita su autoridad antigua (`banned_until=infinity`). Los otros sujetos/social siguen funcionando. Reactivar GoTrue para ese sujeto exige una operación explícita de rollback y contraseña segura; volver al flag anterior no restaura su contraseña antigua.
- [Seguro] RLS deny-by-default en tablas privadas; rol `asisteam_auth` sin herencia, propiedad, bypass ni acceso directo a tablas: ejecuta solo la frontera SQL `auth_operation`. El rol API no puede leer hashes/refresh/recovery. La migración cambia únicamente la lectura de email dentro de `accept_invitation`, con aserción explícita del cuerpo esperado; las reglas CB-06/R1/cupos no se reescriben.
- [Seguro] Límites en PostgreSQL: login cinco intentos por email/15 min (limpia al éxito), 30 por IP; registro/recovery/reset/refresh/logout/password diez por IP/15 min. Claves de límite hasheadas con secreto, sin email/IP en claro. API rechaza cookies; proxy web debe acreditar IP con secreto privado.

## Activación y rollback

[Seguro] API requiere conjuntamente `NATIVE_AUTH_DATABASE_URL` (rol dedicado, misma DB), `NATIVE_AUTH_SECRET` (≥32 caracteres aleatorios), `NATIVE_AUTH_ISSUER` (origen HTTPS estable), `NATIVE_AUTH_WEB_URL` (origen HTTPS del web) y `NATIVE_AUTH_PROXY_SECRET` (≥32 caracteres). Recovery utiliza `RESEND_API_KEY` + `INVITATION_EMAIL_FROM`. Credenciales de rol se provisionan fuera del repositorio; la migración lo crea NOLOGIN. Los secretos nunca llevan prefijo `NEXT_PUBLIC_`. Rotar la clave JWT invalida access anteriores; planificar re-login.

[Seguro] Web: `ASISTEAM_TRANSPORT_AUTH=nest`, `ASISTEAM_AUTH_WEB_ORIGIN`, `ASISTEAM_API_ORIGIN`, secreto privado del proxy y TODOS los módulos `ASISTEAM_TRANSPORT_{GROUPS,PROFILE,MEMBERS,INVITATIONS,ACTIVITIES,ATTENDANCE,REPORTS,BILLING,ANNOUNCEMENTS,QR,STORAGE}=nest`. `ASISTEAM_API_SUPABASE_URL` debe coincidir con `NEXT_PUBLIC_SUPABASE_URL`. Configuración mixta lanza `native_auth_requires_nest`: JWT propios no autorizan PostgREST. El reverse proxy debe sobrescribir `X-Forwarded-For` y no permitir que un cliente forge IP; API confía en esa cabecera solo acompañada por su secreto de proxy.

[Seguro] Cookies `asisteam-access` y `asisteam-refresh`: HttpOnly, SameSite=Lax, Path=/, Secure en producción; nunca localStorage. Server Actions verifican Origin. Middleware valida sesión/consentimiento/permisos, renueva cookies de request y response y marca contenido privado `no-store`. Refresh simultáneos se comparten dentro del proceso Next mientras están en curso; entre réplicas o peticiones separadas el protocolo estricto puede detectar replay y exigir re-login, sin tolerancia que debilite la revocación.
